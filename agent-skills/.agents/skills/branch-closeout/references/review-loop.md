## What the sources actually prescribe

### Reviewer roles and delegation

- **qa-swarm is review/publication, not a fix loop.** It captures base, changed paths, triple-dot diff, commit log and HEAD SHA. Without a PR it defaults to `master`, then `main`, and produces a terminal report only. With a PR it posts findings and a summary. [Q, Steps 1 and 5]
- **Cheap-first router:** exactly one first-pass `Explore` agent, deliberately unable to spawn reviewers itself. It reads full diff plus at least 50 surrounding lines above/below each change, returns findings and a delegation plan. Parent orchestration executes that plan. Empty delegation is valid for genuinely small/low-risk work. [Q, Step 3a]
- **Objective escalation overrides self-rated confidence:** at least one delegation for roughly >400 changed lines, production deploy/release paths, auth, permissions, billing, migration or concurrency. Risk signals additionally include secrets/crypto, destructive writes, cross-file effects, uncertain framework/async behavior and HIGH/CRITICAL findings needing confirmation. [Q, Step 3a]
- **Independent scoped lenses:** delegated agents receive only their scoped diff, lens and necessary context, not other reviewers' findings or roster. Independent delegations run in parallel; a second lens/pass is allowed; total delegation cap is six. This cap does not bound nested qa-team agents. [Q, Step 3b]
- **qa-team:** specialists cover security, database, reliability, compatibility, data integrity, performance, frontend and copy; it requires at least four specialists plus two generalists every run. Generalist A checks correctness/safety; B attempts production breakage. Copy is explicitly nonblocking. qa-swarm tells this lens to skip diff collection and return findings rather than write `QAREPORT.md`. [Q, target 1; QA, Steps 2–4]
- **Paul lens:** coupling/fragility, rollout measurability, naming, mixed abstraction levels, type safety, caller empathy and boundary tests. Prefer 3–5 useful comments, concrete alternatives and blocking only for correctness/security; not a linter. Its native persona/voice should not be mistaken for an actual human review. [P]
- **XP lens:** correctness/tests first, intent, meaningful duplication, unnecessary parts, premature abstraction, testability and future maintainability. Smells are hypotheses, not proof; distinguish bugs from optional refactors; avoid abstraction merely because two things look alike. [X]
- **Security lens:** demonstrable source-to-sink exploit chains and missing controls, not hardening preferences. qa-swarm explicitly overrides standalone input gathering, clarification, test-writing and interactive fixes; it retains Description, Data flow, Exploit, Fix, Confidence and category tags. [Q, target 4; S]
- **Systems lens:** load only when selected; trace user-visible path/shared boundary, test common-cause against an alternative, compare local vs narrow shared fix. Requires concrete related evidence; no broad search by default and no speculative architecture comments. [Q, target 5]
- **Model policy is harness-specific.** Q explicitly says resolve supported models first and honor caller override. The named ladders/prices/aliases are source-local claims, not portable facts. Missing skill bodies are surfaced as gaps; do not invent their conclusions. [Q, model roster and graceful degradation]

### Evidence, severity and finding shapes

**Source security threshold:** require concrete controlled input, every source-to-sink hop with file/line, missing control, specific exploit request/impact and real entrypoint reachability. Drop the finding if any of these cannot be established; do not flag framework-protected input, dead/unreachable code, generic rate limits/WAFs/monitoring, or hypothetical prompt injection without downstream impact. Confidence names the assumption that could invalidate the claim. Choose the lower severity if uncertain. [S, Calibration, Methodology, Output format and Severity rubric]

S severity examples: CRITICAL includes unauthenticated RCE, cross-tenant read/write, full takeover and destructive cross-tenant agent action; HIGH includes SQLi, privilege escalation, sensitive IDOR and agent exfiltration; MEDIUM includes stored XSS, internal-network SSRF and important-state CSRF; LOW includes interaction-dependent reflected XSS and low-impact disclosures. Some broad LOW checklist entries say “missing hardening with no demonstrated impact,” in tension with Calibration; retain the stricter exploit gate in a local adaptation. [S]

Q returns a text protocol, not JSON:

```text
STRUCTURED_FINDINGS:
- file: <path> | line: <number or general> | severity: <CRITICAL|HIGH|MEDIUM|LOW|NIT> | reviewer: <tag> | body: <comment>
OVERALL_SUMMARY:
<assessment>
DELEGATION_PLAN:              # router only
  danger: <LOW|MEDIUM|HIGH|CRITICAL>
  confidence: <HIGH|MEDIUM|LOW>
  delegations: <model/lens/scope/reason entries, or empty>
```

No findings is explicitly `(none)`, not an omitted response. Security tags can be `security-audit/idor`; QA tags can be `qa-team/database`. Merge findings within five lines or clearly describing the same concern and preserve independent reviewer provenance. Convergence raises source confidence, not demonstrated impact. [Q, output and synthesis]

Q's aggregate verdict is count-based: any CRITICAL → CRITICAL/BLOCKED; 2 HIGH or 1 HIGH + 2 MEDIUM → HIGH/REQUEST CHANGES; 1 HIGH or ≥3 MEDIUM → MEDIUM/APPROVE WITH NITS; only LOW/NIT/none → LOW/APPROVE. QA counts reviewer-level risks whereas Q counts findings. This is not a sound local ship gate: **one confirmed HIGH becomes “approve with nits,” and one or two MEDIUM findings without HIGH have no explicit aggregate case.** [Q, Step 4; QA, Step 4b]

### Triage and autonomy

T uses three judgment buckets for all-bot threads: actionable/clear, nit/non-actionable, ambiguous. Auto-action requires HIGH/CRITICAL **or convergence**, a concrete fix, localized edits, and no new dependency/design/scope decision. Nits/speculation/duplicates/already-addressed findings get reasoned disposition; ambiguous bot findings go through A's autonomy ladder. [T, Steps 3–4 and Judgment rules]

A's ladder is (1) just-do-it for an unambiguously better, essentially single-option, reversible change; (2) choose an option, implement and report rationale/alternative for “recommend and ask”; (3) stop-and-ask for genuine uncertainty or unjustified violation of simple-design rules. **T's second tier commits and pushes before asking; it is not prior approval.** Missing A defaults to defer. A cautions against unrelated consistency edits and forced extraction. [T, paul-pair gate; A]

T's sub-step output is JSON with `head_sha_in`, `new_head_sha`, `qa_swarm_ran`, `qa_swarm_marker_sha`, `resolved`, `actioned`, `promoted`, `deferred_threads`, `unresolved_actionable_remaining`, `narration`. Parent owns review-marker state; sub-step skips PR resolution and fresh qa-swarm and never asks the user. Every fetched unresolved/non-outdated thread must have one reconciled disposition, with reason or fix SHA. Counters need explicit exclusive meaning because an actioned/promoted thread is also physically resolved. [T, dual mode and Step 5]

### Human vs bot threads and remote behavior

- Inspect **every participant**, not only opening author. Automation is identified via GitHub Bot type, bot account/name patterns or the exact automated-comment header (because the skills post under a human user's account). Any human or uncertain participant makes the entire thread human: defer, do not auto-edit, reply or resolve. Standalone may offer an approved trivial fix, but leaves the human thread open for the author's response. [T, Steps 3–4]
- Every all-bot resolution requires a **successfully posted visible reply first**. Fixed reply names commit SHA/evidence; dismissal explains why. Reply failure leaves the thread open and is reported. Every automated comment/reply is labeled as automation. [T]
- Actionable/promoted fixes follow edit → stage → commit (`fix: address qa-swarm …`) → `git push` → reply with SHA → resolve. T does not specify a test/build/lint gate before this sequence, nor remote/branch protection checks. It explicitly does not rebase/update base, watch CI or manage stamphog; sibling shepherd skills own those jobs. [T]
- Q posts a `COMMENT` review anchored to captured HEAD, with inline findings plus one top-level sticky `<!-- qa-swarm-summary -->` comment. Later rounds upsert summary and compact history; **inline findings are not deduplicated across rounds**. Textual APPROVE/REQUEST CHANGES is not the API's review event. [Q, Step 5]
- Public comments must not expose raw production event/user/revenue counts; Q recommends percentages/ratios. This does not replace general secret/PII review. [Q, bot identifier section]
- Stale bot reviews: skip outdated inline threads and top-level comments whose referenced commit is not HEAD. If top-level timing is ambiguous, source prefers waiting rather than stale fixes. Ignore stamphog approval-dismissal protocol noise. [T, Step 4]

### Re-review and termination

T's standalone first invocation always reviews; later loop invocations review changed HEAD only when changes since marker include a non-`.md`/`.txt`, non-whitespace file. Skipping qualifying changes requires user confirmation; “review fatigue” is not grounds. Marker is captured reviewed HEAD, not evidence of verification success. [T, Step 2]

T is **one-shot**, does not sleep/self-loop, and stops when PR is closed/merged, all threads are classified/handled/deferred, or user interrupts. A single ambiguity is not an early stop; continue independent work and surface deferral. “All classified” is not “all fixed” or “CI green.” Q is likewise one review pass; six is its delegation cap, not a fix-round limit. [T, Step 5 and Terminal conditions; Q]

S's standalone **local branch audit differs from Q's review-only override**: write regression tests at the real entrypoint, observe failure before approved fix, then observe passing reproducer and adjacent tests. Ask explicit fix permission; minimal fixes only. Existing public exploitable weaknesses may require private disclosure rather than publishing in a PR. For the desired closeout skill, this test responsibility belongs to an authorized fixer/verification phase, not to read-only reviewers. [S, Reproducer tests and After reporting]

## Proposed local pre-PR adaptation (not source behavior)

1. **Split review from delivery.** Dedicated reviewers are read-only and independent from the implementer. They cannot stage, commit, push, create/comment on PRs or resolve threads. One parent/fixer integrates validated findings and later delivery owns authorized commit/push/draft PR. Existing PR detection must never silently turn local review into remote publication. This adapts Q's no-PR report mode and T's separation from CI orchestration. [Q; T]
2. **Capture exact scope.** Discover repository instructions, intended base/upstream and current branch; record base SHA/merge-base, HEAD and initial tracked/untracked worktree state. Triple-dot HEAD review alone excludes unstaged/staged/untracked changes. Either review a clearly frozen dirty-tree snapshot too or report exactly what is omitted; do not commit user work just to obtain review input. If HEAD/worktree/base changes during review, invalidate or reconcile affected findings. Q's master/main fallback is not a safe generic base selector. [Q, Step 1; QA, Step 1]
3. **Use one correctness reviewer plus a justified specialist, not a copied swarm minimum.** Preserve objective escalation and independent evidence; constrain fan-out at parent level, including nested agents. Select supported harness roles/models; use repository-specific expertise rather than Paul impersonation/PostHog conventions. Optional XP/design advice must not become mandatory refactor churn. [Q, Step 3; QA, Step 2; P; X]
4. **Gate each finding on evidence, not votes.** Require changed-code relationship, concrete reachable failure/impact, precise location, assumptions and specific bounded fix. Revalidate against current code before action. Deduplicate by root cause, not just proximity; independent agreement is useful but not authorization, severity escalation or exploit proof. Keep material bugs separate from advisory nits, and never label absent reviewer coverage as a HIGH code defect (Q permits this fallback). [S; Q, synthesis/graceful degradation]
5. **Maintain a local finding ledger.** Stable ID, reviewed snapshot, location, severity, impact/evidence, reviewer provenance, suggested fix, disposition (`fixed`, `rejected` with evidence, `deferred` with reason), fix SHA when available, and observed verification result. Separate coverage gaps from code findings. Report actual roles that completed; failure/empty output must not look like “no findings.” [Q, output; T, report; QA, reconciliation]
6. **Fix only established in-scope problems.** Use the narrow, repository-idiomatic fix, with regression test where appropriate. Do not import T's convergence bypass or A's post-push “recommend and ask” for consequential alternatives, new scope/dependencies or architectural choices. Preserve user's unrelated changes; stage only intended files/hunks and do not force-push, amend/rebase or bypass hooks by default. [T, auto-action/gate; S, minimal approved fix]
7. **Verification owns truth.** After fixes, authorized verification runs repository-required checks and captures command, result and tested SHA/tree. A reviewer verdict is not a successful test; an old pass does not validate new edits. Re-review substantive fixes/affected contracts and reverify after subsequent changes. Report unavailable checks as unavailable, never passing. [S, local reproducer loop; T, review marker]
8. **Bound the loop without claiming false cleanliness.** Finish when no evidence-backed autonomous fixes remain, review applies to final snapshot and required available checks are observed successful. Continue unrelated work despite a deferred issue; report unresolved important findings, missing coverage/checks and repeated nonprogress as blockers/decisions. Add a small explicit round/delegation cap and repeated-finding/no-progress detection; on hitting it hand back a precise state, not “ready.” Draft PR creation, if authorized despite deferrals, must disclose them rather than imply approval. [Q, delegation cap; T, terminal/deferral rules]
9. **Threads are an optional existing-PR mode.** Default pre-PR closeout has no thread mutation. If separately authorized, preserve the human-participation gate, full successful-reply-before-resolve invariant and stale-HEAD checks; report human threads for author's action. Recheck participants immediately before remote mutation. [T]

## Source pitfalls that must not be copied blindly

- **Pagination violates the human gate:** T queries `reviewThreads(first:100)` and `comments(first:20)` with no `pageInfo`/cursor loop. More threads disappear; a human reply after comment 20 can be missed, falsely authorizing bot action. Paginate both levels before claiming full coverage or resolving. Its stale-top-level guidance also lacks an explicit top-level-comment fetch in the shown workflow. [T, Steps 3–4]
- **Truncation/autonomy conflict:** T refetches full opening body only for truncated actionable threads; ambiguous threads can be promoted into edits without that same explicit refetch. Read full relevant discussion before any fix/dismissal and ensure no clipped constraint changes interpretation. [T, full-body section and paul-pair gate]
- **Automation identity is heuristic:** substring matching (`cursor`, `veria`, etc.) and user-pasteable headers are not authentication. Unknown users and human quotations of the header should not authorize resolution; require configured exact trusted bot identities/provenance where possible and default human. [T, participant classification]
- **`isOutdated=false` is not demonstrated current-HEAD correctness:** source treats it as sufficient inline staleness filter, but code/assumptions still need current-snapshot revalidation before fixing. Earlier declined/deferred findings also need re-evaluation when HEAD or participant state changes, not permanent omission. [T, stale rule and deferred-thread filter]
- **Nested fan-out/cache machinery is nonportable:** QA requires ≥6 agents and relies on Desktop Workflow scripts, identical-prefix caching, a first-claim warmup heuristic and persona queue. Claim script uses filesystem rename then exits; claiming twice consumes a second persona. Source explicitly requires reconciliation and reports failed reviewers. A local skill should normally assign explicit read-only scopes directly, avoiding queue/cache scaffolding unless this harness genuinely needs it. [QA, Step 3; JS; SH]
- **Serialization is not a trust boundary:** JS safely JSON-encodes prompt content, escapes U+2028/U+2029, uses single-pass placeholder replacement and reads >200 KB diffs from disk; these avoid script/template corruption but do not make commit messages/diffs/comments trusted instructions. Keep repository/web/thread text as data and never execute embedded suggested commands. [JS; S, AI/MCP trust boundaries]
- **Conflicting nested instructions require explicit override:** P natively forbids severity lists/trailing summaries, whereas Q requires both; QA natively writes repository-root `QAREPORT.md`, whereas Q tells it not to. Q's global header invariant conflicts with its sample unlabelled review-body string, and sticky summary begins with HTML marker before header. Preserve semantic contracts at orchestration boundaries instead of copying examples verbatim. [P, format; Q, output/Step 5; QA, report]
- **Source defaults can create noise or inappropriate mutation:** Q automatically posts when a PR exists and republishes inline comments each round; T commits/pushes clear fixes with no explicit verification gate, resolves non-actionable feedback and chooses multi-option solutions before asking. None of this is implied authorization for a local branch-closeout skill. [Q, Step 5; T, Steps 3–5]
- **Doc-only is not always behavior-free:** T's extension-based skip rule can miss executable documentation/config embedded in text. Classify semantic effects and repository conventions rather than blanket `.md`/`.txt` exemption. [T, Step 2]
- **Disclosure:** publicly publishing exploit reproductions/fixes for existing production weaknesses can expose an undeployed vulnerability. S explicitly routes existing exploitable weaknesses privately when disclosure risk requires it; an automatic draft PR is still publication. [S, After reporting]
